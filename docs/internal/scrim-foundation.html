Scrim foundation contract

Scrims remain a separate Turnier domain. Tournament matches and Scrim matches share only storage-independent result mappings; they do not share a lifecycle.

Production read model

The read adapter queries the existing scrim.* schema directly. It does not discover tables dynamically and does not return raw table dumps.

  • Participants include the current status, source, availability and structured availability fields.
  • Teams include their current coach, Discord references, default time window and typed team members with rank, Discord ID, roles, availability, structured availability and notes.
  • Matches retain independent status and lobby_state fields, an optional second team and the canonical selected result from scrim.selected_match_results.
  • Match-request batches contain typed requests, structured slots and participant-level slot responses. The second team may be absent for an open opponent.
  • Lagebild snapshots expose typed metadata and evidence references, not a schema-wide JSON mirror.
  • All wire identifiers are serialized as strings. Database-backed integer identifiers must be positive decimal strings at the boundary.
  • Raw result, lobby and privacy JSON is not exposed by reads.

Match requests

  • A batch needs at least one pairing. Every pairing needs two to five valid weekly time windows, supplied either once for the batch or for that pairing.
  • A team may occur only once in a batch and may not already occur in another active request window.
  • Availability counts, starter counts, missing responses and replacement needs are derived from the current roster and participant responses.
  • The planning request must contain deadline_at. Recommendation and replacement facts remain hidden until the deadline has passed.
  • The legacy tie-break is preserved: most available participants, then most available starters, then the first original slot.
  • A released slot is selected before a calculated recommendation when replacement needs are derived.
  • Historical participant responses remain readable after roster changes; stale responses do not abort the complete read model.
  • Scrim history contains only non-cancelled matches with a canonical selected result. Finished lobby state, raw result JSON and unselected fetched refs do not make history.

Match core

  • Canonical result sides are team0 and team1.
  • Bracket keeps its existing 0/1 convention; Group keeps its existing 1/2 convention and winner-ID precedence.
  • The shared crate defines result and finality mappings only. It does not define transitions or terminal statuses.
  • Existing same-team behavior is preserved; the shared mapper does not add a new duplicate-team guard.

Internal API

All routes use the prefix /internal/turnier/v1/scrims, require a loopback peer and require the token from TURNIER_INTERNAL_API_TOKEN. BFF callers use TURNIER_INTERNAL_API_BASE_URL for the loopback origin.

Reads

  • GET /command-center, /me, /pool, /coaches, /teams and /history.
  • GET /teams/{id}/board and /teams/{id}/timeline.
  • GET /match-requests/defaults, /match-request-batches, /match-request-batches/{id}, /match-requests/{id}, /match-requests/{id}/status-preview and /match-requests/{id}/replacement-needs.
  • GET /replacement-needs/{id}/candidates.
  • GET /matches and /matches/{id}.
  • GET /blocks/{id}/announcement-preview and /actions/{id}.

Mutations

  • PUT /me/availability; POST /signup and /teams; PATCH /teams/{id} and /participants/{id}.
  • POST /teams/{id}/announce, /teams/{id}/suggest, /teams/{id}/substitute and /participants/{id}/resync-discord.
  • POST /match-request-batches, /match-requests/{id}/release, /match-requests/{id}/reminders and /match-requests/{id}/status-publications.
  • POST /replacement-needs/{id}/requests and PATCH /replacement-requests/{id}.
  • POST /matches, PUT /matches/{id}/lobby-code, POST /matches/{id}/match-ids, POST /matches/{id}/result-fetches and PATCH /matches/{id}/result-refs/{ref_id}.
  • POST /blocks/{id}/announcement-publications.
  • POST /interactions/match-request-response is the canonical DL-Bots relay boundary using schema turnier-scrim-match-request-response:v1.

The BFF planning body is strict and typed: {technical_template_key?,deadline_at,slots?:[{day,from_minute,to_minute}],pairings:[{team_a_id,team_b_id,slots?}]}. Pairing IDs are strings, team_b_id may be null for open opponents, omitted technical_template_key uses the default technical template, and each effective slot list must contain two to five valid minute windows; per-pairing slots override the global list.

Every mutation requires X-Request-Id and a persistent Idempotency-Key; both must satisfy the same domain-ref format as scrim.is_domain_ref. BFF actor identity is accepted only through X-Actor-Discord-Id and X-Actor-Display-Name. Management actions require an active coach; there is no admin/mod fallback. Participant interactions require the actor's own Discord identity and team membership.

The DL interaction body uses schema turnier-scrim-match-request-response:v1 with fields schema_version, event, idempotency, action, request, team, slot, interaction, guild, channel, message, actor and actor_role_ids. The request must still be open and the channel/message pair must match the original team query.

Runtime control

Reads are allowed after loopback/token and actor authorization. Mutations acquire the runtime advisory transaction lock, then read scrim.runtime_control from the central database; only operational_writer=turniere with mode draining or turniere may mutate. Otherwise the API returns HTTP 409.

Planning batch create, participant match-request response and match-request release persist transactionally in Postgres, record scrim.command_receipts for idempotent replay and write pseudonymous scrim.audit_events. Other capabilities return HTTP 501 with {available:false, verified:false, message} without deserializing or validating the unused body. There is no SQLite path and no dual-write.
