# DDC Turnierplattform – kontrollierter Lasttest (23. November 2026)

**Status:** Baseline gegen das **laufende, unveränderte** Rust-Backend. Die Optimierungen in Draft-PR #34 sind hier **nicht** produktiv und wurden in diesen Messwerten noch nicht nachgemessen.

## Sicherheitsrahmen

- Nur drei bekannte öffentliche GET-Endpunkte: `/api/health`, `/api/draft/heroes`, `/api/tournaments/17`
- Zwei Wege: `http://127.0.0.1:8900` (Rust direkt) und `https://deutsche-deadlock-community.de/turnier` (HTTPS/Caddy)
- Maximal 8 parallele Verbindungen, **kein** POST, kein Admin-Token, kein Login, keine schreibende DB-Operation
- Pro Endpunkt und Weg: 8 Warm-up-Aufrufe; danach je 24 / 56 / 96 Aufrufe bei 1 / 4 / 8 parallelen Clients
- Insgesamt **1.056 gemessene Requests**, keine HTTP-Fehler, keine Timeouts und keiner der warmen Requests über 300 ms
- Node.js mit Keep-Alive-Agent (Verbindungen werden wiederverwendet), `p95` als nearest-rank-Quantil, Zeit bis vollständig empfangener Antwort
- Test **vom Server selbst aus**. Die öffentlichen Domain-Ergebnisse messen deshalb nicht die reale geografische Latenz eines Spielers.

### Zusätzlicher Kurztest bei 16 parallelen Clients

Der gleiche laufende öffentliche Turnier-Handler wurde **direkt über localhost** mit weiteren 96 GET-Anfragen und **16 parallelen Clients** belastet (während andere Rust-Builds auf dem Shared-Host liefen):

| Messung | Wert |
|---|---:|
| Antworten mit HTTP 200 | 96/96 |
| p50 | 92,4 ms |
| p95 | 295,1 ms |
| p99 | 330,3 ms |
| Anfragen über 300 ms | 4/96 |
| Kurzzeitiger Durchsatz | ca. 92 Requests/s |

**Folgerung:** Bereits bei 16 Clients wird das akzeptable Maximum (300 ms) gelegentlich überschritten. Die 8-Client-Werte allein reichen also nicht als Freigabenachweis. Der Einfluss konkurrierender Builds darf nicht mit DB-Sättigung gleichgesetzt werden.

### Cold Connection (separate kleine Stichprobe)

16 **neue** HTTPS-Verbindungen zu `/turnier/api/tournaments/17`, jeweils ohne Keep-Alive, seriell: p50 **59,1 ms**, p95 **1.027,9 ms**, höchster Wert **1.027,9 ms**. Kein HTTP-Fehler. Ein starker Kaltstart-Ausreißer zeigt, dass die Warm-Connection-Metriken nicht mit dem ersten Webseitenaufruf gleichgesetzt werden dürfen; die Stichprobe ist für ein belastbares Cold-p95 noch zu klein.

## Codeanalyse und Optimierung in PR #34

1. Öffentlicher Turnier-GET: fünf unabhängige Teilmodelle werden mit `tokio::try_join!` statt seriell geladen.
2. Öffentliche Teamroster: Mitglieder und offene Bewerbungen **jeweils in einem Batch**, statt je Team zwei weitere Datenbankabfragen (`2×N`).
3. Admin-Turnierdetails: begrenzte parallele Team-, Mitglieder- und Rangauflösung statt serieller Steam-/Discord-Lookups.
4. `SteamRankResolver::rank_profiles`: Deduplizierung und max. vier parallele Abfragen statt serieller Schleife.
5. `Server-Timing: rust;dur=...` und Warnung für Rust-Requests über 300 ms.
6. React Query: längere Stale-Times und reduzierte Hintergrund-Abfragen.

## Ziel und notwendiger Nachtest

- **Ideal:** p95 unter 50 ms für typische lokale Rust-API-Abfragen und warme, einfache öffentliche APIs.
- **Gut:** warme öffentliche API p95 unter 100 ms.
- **Akzeptabel:** unter 300 ms für normale öffentliche Requests.
- **Gesondert messen:** neuer TLS-Verbindungsaufbau, Client-Standort, Browser-LCP/Interaktivität, komplexe Admin-API mit authentifiziertem Testkonto.
- Nach Rust-CI auf aktuellem Compiler und Deployment auf einer **isolierten Staging-Instanz** mit realistischer DB: identischen Test erneut ausführen; bei Bedarf 16 Clients erst nach kontrollierter Freigabe. Erst wenn Staging-Build, Ergebnisdaten und p95 stimmen, produktiv ausrollen.

Zum Reproduzieren (auf freigegebenem DDC-Host):

```bash
node scripts/perf/bench-readonly.mjs local
node scripts/perf/bench-readonly.mjs public
```

**Nicht** für fremde Domains, Schreib-Routen oder unbegrenzte Last verwenden.
